## 安全专项：默认不可信

## 安全基线

对外输入一律不可信，这是默认前提。任何“只给内部用”的接口，最终都可能暴露在外部流量前。

## 五层防护

1. 输入规范化与白名单校验。
2. 反序列化对象过滤。
3. 命令执行彻底禁用动态拼接。
4. 依赖漏洞扫描前置到 CI。
5. 审计日志保留关键证据字段。

## 关键示例

```java
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "maxdepth=5;maxrefs=1000;com.example.dto.*;!*"
);
ObjectInputStream ois = new ObjectInputStream(in);
ois.setObjectInputFilter(filter);
```
```java
if (cmd.contains(";") || cmd.contains("&&")) {
    throw new SecurityException("禁止动态命令拼接");
}
```
## 组织层面动作

- 代码评审增加安全核查项。
- 新增依赖默认先过漏洞扫描。
- 应急演练覆盖“已被利用”场景。

九月安全专项后，默认不可信成了团队共识。

## 深入拆解：为什么这类问题总在高峰期爆发

在 **开放平台网关** 里，外部输入面过大 往往不是一个“单点 bug”，而是多个小问题叠加后的系统性结果。常见链路是：

- 入口流量突刺导致排队增长；
- 排队增长放大超时与重试；
- 重试放大下游压力；
- 下游波动反过来拖慢主链路；
- 观测不完整时，团队会误判根因并继续叠加改动。

要打断这条链路，必须先把“正确性边界”写清楚，再谈吞吐优化。没有边界，优化很容易变成风险转移：你把一个指标做漂亮了，却把问题藏到另一个时间窗口。

## 生产落地蓝图（可直接执行）

1. 定义不可破坏语义：例如幂等、顺序、余额不为负、状态不可回退。  
2. 建立统一预算：超时预算、重试预算、队列预算必须统一，不允许各层随意叠加。  
3. 做资源隔离：CPU 密集、IO 密集、后台批任务至少分三类资源池。  
4. 建立降级路径：可选能力随时可关，核心能力优先保活。  
5. 做压测基线：固定流量模型，记录 P50/P90/P99/P999 与错误分布。  
6. 做灰度机制：小流量观察 30-60 分钟后再扩容，不跨越式放量。  
7. 做回滚预案：每次改动必须有“分钟级可执行”的回滚步骤。  
8. 做复盘沉淀：把经验写进 runbook，减少对个体经验依赖。

## 指标与容量模型

我通常会在看板里同时放四组指标，避免“单指标幻觉”：

- 用户体验层：成功率、超时率、P99/P999。
- 系统资源层：CPU、堆/堆外内存、线程池活跃度、队列积压。
- 依赖稳定层：下游失败率、RT 分布、熔断命中次数。
- 稳态演进层：日常波动、峰值窗口、发布前后对比。

容量规划时，建议留出至少 30% 的瞬时余量。原因很现实：线上波动不是线性发生，异常往往是“突发叠加突发”，余量不足时任何局部抖动都会被放大。

## 典型踩坑样本

- 只优化平均延迟，忽略尾延迟，结果用户投诉仍然集中。  
- 把重试当可靠性手段，结果在下游波动时形成重试风暴。  
- 变更多点同时进行，导致无法判断哪个改动生效。  
- 没有统一日志字段，故障发生后证据链断裂。  
- 回滚脚本未经演练，关键时刻无法快速恢复。

## 安全发布前置条件

- 所有高危输入路径完成白盒扫描。
- 所有依赖完成漏洞级别评估并有处置意见。
- 所有动态执行路径确认已禁用或强约束。
- 所有审计字段在日志平台可检索可追溯。

安全不是“上线后补洞”，而是“上线前防洞”。

## 复盘后的个人原则

- 先证据后结论，先边界后优化。  
- 先保活后提速，先可回滚后放量。  
- 先统一策略再做局部微调，避免模块各自为战。  
- 任何“高阶技巧”都要落在可观测、可演练、可交接上。  

如果把这四条守住，输入校验、最小权限、漏洞前置 这类高阶主题就不会停留在“概念理解”，而是能稳定变成生产能力。

## 深水区案例推演

下面用一个更贴近线上的推演模型，说明为什么 **输入校验、最小权限、漏洞前置** 必须体系化处理，而不能靠某个参数“救全场”。

### 案例 1：高峰入口流量叠加下游抖动

在 开放平台网关 这类链路里，入口流量通常不是平滑增长，而是“脉冲式突刺”。当突刺遇到下游轻微抖动时，系统会先出现排队增长，随后触发超时和重试。重试本意是提升成功率，但在预算缺失时会把局部抖动放大成全链路拥塞。这个阶段如果只盯平均延迟，团队往往误判为“总体没问题”，直到用户侧开始出现明显超时。

### 案例 2：观测面不完整导致误诊

很多团队只保留接口级监控，不看线程池、队列、锁、GC、下游 RT 的联动。结果是故障发生后只能看到“慢”，却不知道“慢在哪里”。我在 2024 年做的几次复盘里，超过一半的恢复时间都浪费在“猜根因”上，而不是“修根因”上。把证据链补齐后，恢复时间通常可以压缩 30%-50%。

### 案例 3：改动过多导致结论失真

线上压力下最容易犯的错误，是同时改多个参数并立即发布。短期看似恢复，长期却无法解释“到底哪个改动有效”。这会让后续治理难以复制，团队又回到经验驱动。正确做法是单变量改动 + 固定流量模型 + 同窗口对比，把每次变化都变成可解释结果。

### 案例 4：回滚不可用导致二次事故

不少系统有回滚方案，但没有演练。真正故障时才发现开关语义不清、依赖未就绪、脚本不可执行，最终把一次可控波动拖成二次事故。我现在的硬性要求是：回滚脚本必须在演练中走通，且值班同学能在分钟级执行，不依赖“只有某个人会”。

### 案例 5：语义正确性被性能优化破坏

外部输入面过大 这类问题常见于“先提速后校验”。如果幂等、顺序、一致性边界没写清楚，任何异步化、批处理化、并行化改造都可能把业务语义悄悄改坏。高阶技术真正的难点不在 API，而在“提速同时不破坏语义”。因此我倾向于先写语义契约测试，再推进性能改造。

## 落地行动手册（可给团队直接执行）

### 第一步：建立统一语言

先让研发、测试、运维对关键术语达成一致：什么叫成功、什么叫降级、什么叫可接受失败、什么叫必须回滚。没有统一语言，跨团队协作会大量内耗。

### 第二步：建立统一预算

给超时、重试、队列、并发都设预算，并明确总预算不允许跨层累加。很多线上雪崩不是因为某一层太激进，而是“每层都稍微激进，叠加后失控”。预算统一后，风险可预测性会显著提升。

### 第三步：建立统一观测

至少建设四块看板：体验看板、资源看板、依赖看板、恢复看板。恢复看板尤其重要，它能告诉你“系统恢复速度是否在变慢”，这是稳定性退化的早期信号。

### 第四步：建立统一演练

每月至少演练一次：流量突刺、下游超时、依赖失败、配置回滚。演练目标不是“证明系统完美”，而是“证明团队在不完美场景下仍可快速恢复”。

### 第五步：建立统一文档

把策略、阈值、脚本、联系人、升级路径写成版本化文档。文档不是形式主义，它是把个人经验转成团队能力的唯一低成本方式。

### 第六步：建立统一复盘

每次故障或险情都要回答三类问题：

- 技术层：根因是什么，为什么之前没发现。
- 流程层：哪一步响应慢了，为什么慢。
- 组织层：知识是否只掌握在少数人手里。

只有三层都复盘，系统才会真正进化。

## 结尾：从“会用技术”到“会做系统”

如果只看单点技术，输入校验、最小权限、漏洞前置 也许只是几段代码、几个参数、几个命令。但放到真实生产环境，它其实是“工程纪律 + 观测体系 + 协作流程”的综合能力。2024 年我最深的体会是：真正拉开差距的不是谁懂得更多术语，而是谁能把复杂问题稳定地变成团队可执行的标准动作。
